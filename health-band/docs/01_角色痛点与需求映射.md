## 2. 第 2 类：软件生态与兼容性 ⭐ 专题（用户点名「解决第二个」）

### 2.0 为什么这类痛点在本期「可以被解决」

用户抱怨的 3 条，本质都是**「功能依赖外部平台/生态，而生态不可控」**带来的：

| 用户抱怨 | 本质 |
| --- | --- |
| 信号差、与手机/其他平台消息提醒有延迟，平台间互通不便 | 提醒链路跨设备、跨网络，延迟与失败不可控 |
| 国产软件在设备上匹配度差，有但功能比手机端少很多 | 端侧能力依赖 App/生态移植，功能被裁剪 |
| 数据不准（睡眠记录大量误判），参考价值打折 | 算法输出无质量标记，坏数据被当成好数据展示 |

**本期的根本解法是一个架构决策：终端自治 + 可选只读归档。**

> 判定、提醒、显示、记录**全部在 ESP32-S3 本地完成**，不经过手机、不经过 App、不经过公网；PC 端/同步只做「事后异步归档」，不参与任何实时判定。
> 这样必做功能对外部生态的依赖被降为 **0**：没有信号、没有 App、没装国产软件、断网，久坐提醒照样按 45 min ± 10 s 触发。

这一决策来自原方案 §3.2「终端自治 + 可选归档」，并在本文档中被显式提升为回应第 2 类痛点的**顶层对策**。

### 2.1 痛点 2-A：信号差、与手机/其他平台消息提醒有延迟，平台间互通不便

| 项 | 内容 |
| --- | --- |
| **用户原话** | 「设备信号差，且与手机或其他平台的消息提醒有延迟，平台间互通非常不方便。」 |
| **根因** | 提醒由手机/云端下发，链路为「传感器 → 蓝牙/Wi-Fi → 手机 → 系统通知 → 手环」，任一环节拥塞/断连即产生延迟或丢失；跨平台协议不统一导致互通困难 |
| **本期对策** | ① **提醒本地化**：`SedentaryService` 在设备内维护状态机，达阈值直接驱动 `Ledc`（马达 PWM 4 kHz）与 LVGL 弹窗，链路缩短为「传感器 → 本地判定 → 本地执行」，无网络跳数；② **同步异步化**：Wi-Fi 同步只搬运历史记录，不承载实时提醒，网络慢/断不影响提醒时延；③ **协议自有且最小**：JSON Lines `AUTH/SYNC/ACK` + 按游标补传，不依赖任何厂商推送 SDK 或手机系统通知通道；④ **断网独立工作**：断网时本地环形缓冲 ≥ 7 天，恢复后按游标补传、幂等去重 |
| **需求编号** | **FR-05**（提醒执行，触发延迟 ≤ 1 s）、**FR-18**（本地提醒优先、同步可关闭）、**FR-13**（本地记录）、**FR-14**（按游标补传）、**NFR-02**（久坐计时误差 ≤ 10 s、提醒触发延迟 ≤ 1 s）、**NFR-05**（断网不丢）、**NFR-08**（局域网、不依赖公网） |
| **验收方式** | T-02：静坐 45 min，`45 min ± 10 s` 触发震动与弹窗，用秒表 + 日志时间戳比对；T-09：断网 2 h 期间提醒正常触发，恢复联网后历史记录全部上传且无重复；**对比验收**：关闭 Wi-Fi / 不连接 PC / 不安装任何手机 App，重复 T-02，结果应与联网时一致 |
| **量化指标** | 提醒触发延迟 ≤ 1 s（本地）；久坐计时误差 ≤ 10 s / 45 min；补传 0 丢失、0 重复 |
| **遗留边界** | 本期不解决「手环与手机之间的消息推送互通」——它被明确移出范围（SRS §4.2）。理由是教学原型无手机 App 生态，且该能力对「久坐提醒」这一核心闭环非必要。若后续拓展，建议用 BLE 标准 GATT 服务而非私有推送 |

**设计示意（提醒链路对比）**：

```
传统（痛点来源，延迟不可控）
  IMU → [BLE/Wi-Fi] → 手机 → 系统通知 → [BLE] → 手环马达
        ↑ 信号差 / 平台互通 / 通知延迟 / 跨端协议不统一

本期（对策）
  IMU → ImuFrame 队列 → StepService → SedentaryService → Ledc + LVGL 弹窗
        ↑ 全在本地，0 网络跳数，触发延迟 ≤ 1 s

  历史记录（异步、非实时）→ [Wi-Fi JSON Lines] → PC 端 SQLite 归档
        ↑ 慢/断/无都不影响上面那条链路
```

### 2.2 痛点 2-B：国产软件在设备上匹配度差，有但功能比手机端少很多

| 项 | 内容 |
| --- | --- |
| **用户原话** | 「国产软件在设备上的匹配度差，部分软件即使有，功能也比手机端少很多。」 |
| **根因** | 端侧功能靠「把手机 App 移植/裁剪到小屏」实现，生态适配跟不上，功能被砍；界面与交互依赖外部应用提供 |
| **本期对策** | ① **不移植任何手机 App**：六页面（表盘、运动、心率血氧、体温、久坐、设置）全部由 **LVGL 8.3 原生绘制**，能力自带、不打折；② **必做页完整交付**：表盘/运动/久坐/设置四页 + FR-01 自检页，功能与「手机端」无关，不存在「功能少一截」；③ **未实现页显式降级**：选做页显示「**未启用**」而非留白或灰色不可用按钮，避免「有图标点不开」的适配差体验；④ **单页单任务 + 大字少层级**：为 4.3 寸 800×480 触屏重新设计信息层级（表 3-5 L0/L1/L2/L3），不是把手机布局缩小；⑤ **PC 端只读归档**：明确「服务端不参与实时判定」，PC 端定位为查询/曲线/导出，不假装是完整客户端 |
| **需求编号** | **FR-06**（表盘）、**FR-07**（运动页面）、**FR-08**（设置）、**FR-15**（PC 端只读归档，选做）、**FR-17**（指标解释与测量状态同显）、**FR-18**（不依赖外部生态）、**NFR-01**（≥ 25 fps、切页 < 200 ms）、**NFR-06**（≥ 48 px 触摸目标、90 s 完成主流程）、**NFR-10**（目录即架构，UI 层不越层调用驱动） |
| **验收方式** | 图集「页面原型草图」页 4 个必做页线框评审；NFR-06：5 名非本专业用户，90 s 内完成「看步数—测心率—设阈值」；T-10：短按/长按 2 s/长按 5 s 分别翻页/熄亮屏/回表盘；代码评审检查「ui 不得出现 `i2c_master_`、driver 不得出现 `lv_`」 |
| **量化指标** | 界面 ≥ 25 fps；页面切换 < 200 ms；可点击区 ≥ 48×48 px；首次使用 90 s 完成主流程 |
| **遗留边界** | 不提供第三方应用商店/小程序/手机 App（SRS §4.2）。本期的「功能完整性」以 SRS §4.1 必做清单为准，不以与手机端逐项对齐为准 |

### 2.3 痛点 2-C：数据不准（睡眠记录大量误判），参考价值打折

| 项 | 内容 |
| --- | --- |
| **用户原话** | 「如手环的睡眠记录不精确，存在大量误判，导致数据参考价值打折。」 |
| **根因** | 两个层面：① 算法层——阈值固定、未剔除干扰动作、无质量评估；② 展示层——**把不可信的结果当成确定数值直接显示**，用户无法分辨哪条数据该信，于是「整个数据都不可信」 |
| **本期对策** | **「质量优先 + 不可信不显示」双保险**：<br>① **算法可解释可评测**：计步用「零偏校准 + 低通 + 合加速度 + 动态阈值 + 峰谷对」，用 100 步基准实测误计/漏计率；久坐用 5 min 窗口「≥ 30 步或中等以上强度」定义有效活动，排除拿水杯/打字/抖腿，并给 2 min 起身宽限期防规避；<br>② **信号质量门控**：PPG 先确认佩戴（PPG 直流分量 + 姿态稳定）再采 10 s，质量不合格提示「请保持静止」并**丢弃整个窗口**；<br>③ **无效值显式化**：记录格式中 `hr=0` / `spo2=0` 表示无效，界面必须同显「测量中 / 信号质量 / 未佩戴」状态，**不可信时明确不显示数值**（而不是显示一个可能错的数字）；<br>④ **教师可复现**：自检模式 + 串口日志 + 测试数据集，误判可被定位到具体环节；<br>⑤ **不宣称临床精度**：界面标注「非医疗用途」，精度指标只作为教学评测项 |
| **需求编号** | **FR-02**（50 Hz 采样，丢样 < 0.1%）、**FR-03**（计步，100 步误差 ≤ 3%）、**FR-04**（有效活动定义）、**FR-09**（按需 10 s + 信号质量 + 不可信不显示）、**FR-17**（测量状态同显）、**NFR-03**（误计 < 3%、漏计 < 5%）、**NFR-04**（心率 ≤ ±5 bpm、SpO₂ ≤ ±3%、体温 ≤ 0.3 ℃）、**NFR-09**（分级采样）、SRS §11 合规声明 |
| **验收方式** | T-01：平地 100 步 × 5 组，误差 ≤ 3 步/组；T-05：指夹血氧仪 30 组，心率 ≤ ±5 bpm；**T-06（关键）**：离腕测量，必须提示「未佩戴」且**不显示数值**；T-07：拍桌/坐下/跳下台阶各 20 次，跌倒误报 ≤ 2 次；体温计对照 20–35 ℃ |
| **量化指标** | 误计率 < 3%、漏计率 < 5%；心率 ≤ ±5 bpm、SpO₂ ≤ ±3%；跌倒误报 ≤ 2/60；离腕不显示数值 = 100% 通过 |
| **遗留边界** | **睡眠分期不在本期范围**（SRS §4.2），因此不存在「睡眠误判」。这是主动的范围裁剪：与其做一个不准的睡眠分期，不如把「久坐」这一条链路做准、做可评测。热量估算同理仅作教学展示值，不宣称医学精度 |

### 2.5 「解决」的判定结论

| 判定项 | 结论 |
| --- | --- |
| 每条抱怨是否都落到可编号的需求 | ✅ 2-A→FR-05/13/14/18；2-B→FR-06/07/08/15/17/18；2-C→FR-02/03/04/09/17 |
| 每条需求是否都有测试用例 | ✅ 见 §2.4 与 `04_需求追踪矩阵.md`，无孤儿需求 |
| 是否有可量化判据 | ✅ ±10 s / ≤1 s / ≤3 步 / ≥25 fps / 90 s / 0 丢失 0 重复 / 离腕不显示 |
| 是否诚实地声明了「没解决什么」 | ✅ 手机 App 互通、第三方生态、睡眠分期均列入 SRS §4.2「明确不做」，并逐条给出理由，不含糊带过 |
| 是否与 P0 验收标准冲突 | ❌ 不冲突：全部落在「计步、久坐、表盘、设置」必做范围内，选做项均标记 |

> **结论**：第 2 类痛点在本期不是靠「做一个更好的 App 适配」解决，而是靠**把实时闭环从生态里搬回设备本地**、**把不可信数据挡在显示之前**、**把做不准的功能明确移出范围**三条组合解决。这样既满足 P0 必做范围，也让「信号差/适配差/数据不准」这三条抱怨各自有了可验收的答案。

## 3. 第 3 类：功能表现与算法局限（简表）

| 痛点 | 根因 | 本期对策 | 需求 | 验收 |
| --- | --- | --- | --- | --- |
| 影像能力弱、抓拍差 | 无摄像头/ISP | 明确不做，移出范围 | SRS §4.2 | 范围评审 |
| 心率受摆臂和变速影响波动大 | 运动伪影 + 固定阈值 | 按需 10 s 静止窗口 + 信号质量门控，质量不合格丢弃窗口 | FR-09、NFR-04 | T-05、T-06 |
| 计步受非步行动作干扰 | 单阈值峰检测 | 低通 + 合加速度 + 动态阈值 + 峰谷对 + 5 min 有效活动窗口 | FR-02、FR-03、FR-04、NFR-03 | T-01、T-07 |
| 热量估算不精准 | 无个体参数 | 仅作教学展示值，不宣称精度，界面标注「非医疗用途」 | SRS §11 | 文档/界面评审 |
| 睡眠阶段难准确区分 | 需多模态 + 临床验证 | 不做睡眠分期，聚焦久坐一条链路做准做可评测 | SRS §4.2 | 范围评审 |
| 指标多但缺解释、不知意义 | 只有数值没有语义 | 关键数值附单位与文字（心率红色 +「bpm」）、测量状态与信号质量同显 | **FR-17**、NFR-06 | 原型评审、T-06 |
| **固定阈值不适合所有人，未做到千人千面** | 阈值写死在代码里 | 久坐阈值/震动强度/抬腕开关可在设置页调整，写 NVS 掉电保存；恢复出厂可重置 | **FR-08、FR-16**、NFR-05 | T-08、UC-03 |

> 关于「千人千面」的诚实边界：本期实现的是**「用户可配置阈值」级别的个性化**（可参数化、可持久化、可复位），**不是**基于历史数据自动学习个体基线的自适应算法。后者列入后续拓展，不在本期承诺，避免过度设计。

## 4. 第 4 类：隐私安全与功耗平衡（简表）

| 痛点 | 根因 | 本期对策 | 需求 | 验收 |
| --- | --- | --- | --- | --- |
| 隐私保护弱、资料易泄露 | 上传身份信息 + 公网服务 | 只采健康相关数据；不采姓名/学号/手机号；虚构用户与模拟数据；仅存设备与教师机局域网；不上传公网；同步可关闭；课程结束统一清理；导出 CSV 提示「仅用于教学」 | **NFR-08、FR-18**、SRS §11 | 代码审查 + 数据库抽查 |
| 提高监测频率极耗电，降低频率又漏关键数据 | 全传感器常开同频采样 | **分级采样**：IMU 固定 50 Hz（覆盖 0.5–5 Hz 步态主频）、PPG **按需** 100 Hz（10 s 窗口）、温度 1 Hz；生理参数「按需触发 + 质量优先」；UI 1 s 节流；同步完成即关 Wi-Fi | **NFR-09、NFR-01**、FR-02、FR-09、FR-11、FR-14 | 电流测量 + 任务运行日志 |

> 采样率取舍依据（原方案 §3.3）：实测对比 25 / 50 / 100 Hz，50 Hz 覆盖步态主频且 CPU 不过载。这一「分级」正是把用户所述「频率—功耗—漏数据」三角矛盾变成可配置工程参数的落点。

### 6.1 本轮新增三项选做与本专题的关系

> 用户追加：① 连入 PC 接入大模型询问健康情况（FR-19）；② RAG 检索基于 PC 端收集的数据（FR-20）；③ 手环操控鼠标（FR-21）。三项**均为选做**，挂在本专题「终端自治 + 可选只读归档」的归档支路之后，不改变 §2 对第 2 类痛点的任何结论。

| 新增选做 | 与第 2 类痛点「软件生态与兼容性」的关系 | 必须守住的本专题边界 |
| --- | --- | --- |
| PC 大模型健康问答（FR-19） | 正面回应「平台互通不便 / 数据参考价值打折」：把 PC 端归档数据变成可自然语言查询的答案，不必依赖手机 App 或第三方平台 | 模型**本地/局域网**、不上传公网、不采集真实身份、标注「教学演示，非医疗建议」；回答须附来源 |
| 基于 PC 端数据的 RAG（FR-20） | 正面回应「数据不准、误判导致不敢用」：语料只取自本项目 `records`/`events`，每条回答可追溯到 `(device_id, ts)`，避免大模型凭空编造 | 不接入外部知识库；无归档数据时如实提示「暂无可检索数据」；不把 AI 当数据手册/测试结论/责任主体（附录 C 三条边界仍适用） |
| 手环操控鼠标（FR-21） | 属交互拓展，与第 2 类痛点无直接对应；独立选做 | 默认关闭 + 二次确认 + 一键断开；不自研驱动内核；开启期间不影响久坐提醒与计步主流程 |

> 三项均**不冲击** §2.0「必做功能对外部生态依赖为 0」的结论：它们依赖的是本组自建的 PC 归档，而非手机/第三方生态；且裁剪任一都不影响四条底线。详见 `00_需求规格说明书.md` §3.4、§5.2、§6（NFR-11/12）与 `04_需求追踪矩阵.md`（T-15/16/17）。
